## Public service

`npm run build:node` builds the Node 24 runtime. `npm run start:public` starts the Cloud Run public entry point on `0.0.0.0:$PORT`. The production Dockerfile uses the same pinned Node 24.21.0 image index as the repository check image; its manifest includes amd64. The final image runs as the unprivileged `node` user and contains compiled code, production dependencies and migrations. A local image build is not a deployment or a qualified release digest.

`GET /healthz` reports process health and the build identifier. `POST /` serves the three modern MCP tools through the existing pinned SDK. Other routes, origins, duplicate authentication/protocol headers, upgrades and `Expect` requests are rejected. The service does not trust a forwarded host or construct a public URL from caller headers. Health does not claim database or upstream availability.

Eight active requests fill the process envelope; another request receives 503 and a retry hint. There is no application request queue. The 55-second application deadline starts when Node receives the request headers and covers key admission, body upload, SQL/GCS/upstream work, normalization and response handling. Header reception and socket inactivity have separate server bounds. A disconnected client aborts its request. These process bounds do not measure Cloud Run startup or its external queue.

Authenticated request bodies are limited to 64 KiB and valid UTF-8. An oversized request receives 413 before the transport closes its socket. Responses are bounded to 1 MiB, prohibit cookies, and use `Cache-Control: no-store`. Exceptions at the HTTP boundary produce an empty unavailable response; raw provider exceptions are never logged there. The pinned MCP SDK currently emits a constant warning when a JSON handler is constructed; this contains no request fields and is not suppressed by changing global console functions.

SIGTERM stops new work and permits up to nine seconds for active responses to drain, then aborts remaining requests and closes connections. Responses completed during draining close their keep-alive connection. The entry point has a ten-second process-exit backstop. Normalization workers and database pools close after HTTP draining. Termination during initialization cancels identity retrieval and closes resources that finish initializing later. An unexpected uncaught exception or unhandled rejection emits only a constant `process_failed` event and exits unsuccessfully; the process never resumes after an unknown failure.

## Configuration and identities

The public service requires `LEXCERTA_ENVIRONMENT` (`staging` or `production`), `GOOGLE_CLOUD_PROJECT`, a 40-character `LEXCERTA_BUILD_ID`, `API_KEY_PEPPER`, `COURTLISTENER_CREDENTIAL_ID`, `COURTLISTENER_API_TOKEN`, `LEXCERTA_DATABASE_HOST` and `LEXCERTA_DATABASE_PASSWORD`. The pepper, upstream token and database password must come from environment-specific Secret Manager references. Production keys use the `live` namespace; staging uses `test`. No fixture URL or workstation identity override is accepted by the public entry point.

Resource naming for the forthcoming project configuration is deterministic:

- Neon: separate projects for staging and production in AWS Ohio; database: `lexcerta`.
- Database users: `lexcerta_<environment>_public`, with separate `admin`, `job` and `migrator` roles. These are SQL-created restricted roles, not Neon owner identities.
- Source bucket: `<project>-lexcerta-sources`.

Stage and production must use separate GCP and Neon projects, secrets and identities. Configuration syntax does not prove that isolation; IAM, database grants and cross-environment tests remain required. The public entry point only creates the public database pool. Private entry points and grants must never expose their credentials through it.

`LEXCERTA_DATABASE_HOST` must be a direct `ep-…[.c-N].us-east-2.aws.neon.tech` endpoint. URLs, IP addresses, other regions and `-pooler` endpoints are rejected. The password must be a 32–1024-character printable ASCII secret; provision a random secret rather than a human password. Port 5432, database and service-specific username are fixed by the adapter. No connection URI can override TLS settings. The pinned `pg` driver requires certificate and hostname validation, TLS 1.2 or newer, and enables SCRAM channel binding when offered. Startup authenticates and checks PostgreSQL 18 and the absence of elevated/Neon-owner membership before the service listens. Provider failures are reduced to a constant startup error without their raw messages.

Pool maxima remain public 5, admin 2, job 2 and migrator 1, with minimum zero, ten-second idle removal and five-minute maximum connection lifetime. Direct connections preserve session settings and migration advisory locks. The connection and acquisition deadline is four seconds to accommodate cold activation; the whole SQL operation remains five seconds, including acquisition and retries. A lost idle connection is removed and the next operation may reconnect. There is no connection keep-warm query or background database maintenance loop. Each acquisition and query remains cancellation-bound as described in `postgres-storage.md`.

Create the four restricted roles through SQL and grant only their required schema/table privileges. Neon Console/API-created roles receive `neon_superuser` membership and must not be used as application roles. Enforce connection ceilings 30/4/2/1 and inspect actual server headroom. Keep the bootstrap owner out of service and CI configuration. Rotate a role's password through a controlled Secret Manager version and deployment, accounting for existing connections and revision overlap; after reset, old credentials must fail new connections. Live rotation and connection-capacity evidence remain staging work. [Neon role behavior](https://neon.com/docs/manage/roles)

Google authentication library 11.0.2 remains for operator signature verification. GCS uses attached Cloud Run metadata identity with its existing one-second bounded retrieval and expiry-aware cache. Database passwords are distinct from Google service-account keys; CI still uses workload identity federation and receives no downloadable cloud service-account key.

## Local evidence

The mounted pinned-client test uses real HTTP, Postgres key admission, upstream attempt reservations, source history and the Node normalizer. CourtListener responses and source-object storage are fixtures. It discovers exactly three tools, completes citation and quote verification, and checks source-attempt accounting. Separate tests cover revocation, environment mismatch, modern quota errors, invalid UTF-8, oversized bodies, service concurrency, disconnects and bounded draining.

GCS wire tests separately exercise the native transport, generation preconditions, checksum validation and real socket closure. Metadata identity tests use a loopback transport. These results do not establish live CourtListener response compatibility, GCS authorization, Cloud Run privacy or external pilot use.

`npm run test:container` takes `LEXCERTA_TEST_IMAGE`, the disposable `LEXCERTA_TEST_DATABASE_URL` described in `postgres-storage.md`, and `LEXCERTA_TEST_POSTGRES_CONTAINER`, the name or ID of that PostgreSQL 18 fixture container. The restore drill uses its `pg_dump` and `psql` tools and checks that its published database port matches the fixture URL. Build the image for `linux/amd64` first, with a nonzero 40-character `BUILD_ID` for the saved-image handoff regression. CI uses its actual commit; a local fixture may use forty `a` characters, which must never be reported as a real source commit or release. Optional `LEXCERTA_TEST_DOCKER_HOST` and `LEXCERTA_TEST_DOCKER_CONFIG` select a local Docker daemon. The database fixture's published port must be reachable from Docker through `host.docker.internal`; production databases are rejected by the fixture setup.

The container checks compare compiled runtime files, including shared HTTP/process lifecycle and key storage, to the host build, verify Node 24.21.0/x64/UID 1000, inspect the actual one-CPU/1-GiB limits and run the same public process lifecycle with injected local dependencies. Real Postgres supplies admission and source authority; loopback HTTP supplies CourtListener and GCS responses. The pinned client calls all three tools, an active quote completes during SIGTERM, and SIGKILL preserves charged attempts without publishing the interrupted source. Actual container SQL connections are observed before kill and absent afterward. Both output streams exclude source-text and credential sentinels. The production entrypoint separately fails safely with missing configuration or unavailable database connectivity and networking disabled.

This is a short container lifecycle qualification, not the required 30-minute concurrency-eight soak, sustained-memory proof, actual GCS durability, live Neon qualification or a production-eligible image. Earlier local work-in-progress images deliberately used an all-zero build identifier and predate the saved-image handoff regression. Historical records in `qualification/node-public-2026-09-12/` and `qualification/node-operator-2026-09-12/` cover the earlier Cloud SQL adapter. Their hashes and results must not be presented as qualification of the Neon image.
