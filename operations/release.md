# Release candidates and promotion

The release path must build once, qualify that image in staging, and promote its exact registry digest through production approval. `.github/workflows/release.yml` produces a manually dispatched, fixture-qualified candidate with its saved image bytes and evidence. The preparation command verifies its GitHub origin, extracts its exact file set, loads the saved image and checks its compiled contents. Registry publication is in progress; staging deployment, hosted qualification and production traffic promotion are still unimplemented. A successful candidate workflow will not establish those results.

## Candidate workflow

Dispatch is limited to `main` in the repository and owner with the recorded numeric IDs. The workflow uses read-only repository/Actions permissions, no cloud identity or credentials, and a concurrency group that does not cancel an active release when another is requested. It checks out without persisting a Git credential.

The workflow installs locked dependencies under the pinned Node version, runs all repository and real PostgreSQL checks, builds one amd64 image with the exact commit as `LEXCERTA_BUILD_ID`, runs the container suite, audits dependencies and runs the full thirty-minute fixture soak against that same image. It never calls the smoke mode for qualification. Source acquisition stays behind the existing local fixtures and consumes no CourtListener quota.

After those commands succeed, `scripts/release-candidate.mjs` checks the workflow identity, commit, clean checkout, image architecture/user/build identity and full soak identity. It compares every compiled file with the hashes measured by the soak. It saves the existing image through `docker image save`; it does not rebuild it. All-zero local fixture builds are rejected.

The candidate contains:

- `runtime.tar`: saved image bytes, with a streamed SHA-256 in the manifest.
- `candidate.json`: commit, workflow/run/attempt identity, local image identity, compiled and migration hashes, selected source/lockfile hashes, and hashes for every retained evidence file.
- Repository, PostgreSQL, container and dependency-audit logs.
- The complete soak JSON and sentinel-checked container log, including the measured workload and memory trace.

The manifest stage is strictly `fixture_qualified`. The verifier rejects altered or missing files, symlinks, unexpected file keys, different run attempts/commits, incomplete or smoke soak records, and compiled hashes that do not match the soak. The local engine's `image_id` is not an Artifact Registry manifest digest. Recording and verifying a directory also does not prove its GitHub origin; consumers must use the independent origin check below.

The pinned official artifact action uploads only those named files, retains them for seven days, and does not overwrite an earlier attempt. Failed runs upload separate diagnostic artifacts and cannot produce an eligible successful candidate. Hidden-file inclusion is explicit because the named files live beneath `.release/`; that directory is ignored by Git. The action uses Node 24. Workflow syntax is checked with checksum-pinned actionlint 1.7.12. [Upload artifact action](https://github.com/actions/upload-artifact/tree/043fb46d1a93c77aae656e7c1c64a875d1fc6a0a), [actionlint release](https://github.com/rhysd/actionlint/releases/tag/v1.7.12).

## Downloading a candidate with verified origin

`node scripts/release-download.mjs --run-id <id> --run-attempt <attempt> --commit <sha> --output <fresh-candidate.zip>` reads the actual GitHub run and artifact metadata before downloading anything. It accepts only a successful, completed manual `release.yml` run on main in the recorded repository and owner, at the expected commit and attempt. The artifact name, originating run, repository, branch, SHA-256 and byte length must agree across the listing and current artifact record. Missing, expired, ambiguous, replaced or oversized artifacts fail closed. [GitHub workflow runs](https://docs.github.com/en/rest/actions/workflow-runs), [GitHub artifact metadata and downloads](https://docs.github.com/en/rest/actions/artifacts).

The GitHub token is sent only to fixed GitHub API routes. The signed HTTPS download URL receives no API token, cookies or caller headers, and cannot redirect again. The downloader streams at most the declared size (capped at 2 GiB), verifies GitHub's archive SHA-256, and checks that the run has not started another attempt. The overall deadline is three minutes; individual metadata requests have ten-second deadlines. Failed or cancelled downloads remove their own partial file and preserve an existing destination.

The result is only `download_verified`, with `approval_granted: false`. It does not extract the ZIP, load or execute the saved image, publish to a registry, or deploy. Local tests use explicitly synthetic archive bytes to exercise origin binding, credential handling, truncation, tampering and cancellation. A live ordinary Check run was also rejected without creating an archive. No successful hosted release artifact has been downloaded yet.

## Required staging and production continuation

Run `node scripts/release-prepare.mjs --run-id <id> --run-attempt <attempt> --commit <sha> --output-directory <fresh-directory>` on the trusted release runner. It always obtains origin through GitHub; it does not accept a saved report as proof. It retains the verified ZIP, extracted candidate and `handoff.json` only after all stages pass. Failure removes the directory it created, preserves an existing destination, and does not grant approval. An image loaded before a later failure may remain in the local daemon; the command does not delete shared images.

Extraction uses pinned development dependency yauzl 3.4.0 with strict names and entry-size validation. It allows exactly eight regular files, with no directories, symlinks, special files, duplicate names, filename aliases or encryption. It supports stored and deflated entries, verifies CRCs and limits combined extracted bytes to 2 GiB; the manifest is capped at 4 MiB and individual evidence files at 64 MiB. Archive size and SHA-256 are checked on the same open, non-symlink descriptor before and after extraction. The output directory is private and created exclusively; file modes are set locally rather than restored from archive metadata. The candidate verifier then checks the exact directory contents, run identity, file hashes and soak contract. [yauzl documentation](https://github.com/thejoshwolfe/yauzl).

Image loading must report exactly the expected image ID, so a different archive cannot pass merely because the expected image already exists locally. The loader checks platform, unprivileged user, work directory and build metadata. It runs only a fixed inspection program with no network, read-only filesystem, dropped capabilities, constrained CPU/memory/processes and an explicit Node entrypoint. Node version, UID, build ID and every compiled and migration file must match the manifest. It removes its temporary inspection container. The handoff stage is `image_verified`, still with `approval_granted: false`; this local image ID is not a registry digest. [Docker image load](https://docs.docker.com/reference/cli/docker/image/load/), [Docker image inspect](https://docs.docker.com/reference/cli/docker/image/inspect/).

The [preparation qualification record](qualification/release-prepare-2026-09-13/local.json) covers malformed ZIPs, cancellation, changed content, incorrect image loading and the complete local fixture round trip. That round trip used an actual 86 MB archive and Docker image, but synthetic GitHub responses and synthetic verifier metadata adapted from historical soak evidence. It does not establish a successful hosted release run or a new soak. A real Docker save/load regression is also included in the existing container suite used by both Check and Release candidate.

The in-progress `scripts/release-stage.mjs` command prepares a candidate from fresh GitHub origin, rechecks protections and calls `scripts/release-registry.mjs` to publish into an explicitly selected staging repository. It uses checksum-pinned crane 0.22.1 and independently checks registry digest, manifest bytes, remote blobs and the pulled image identity. The [registry checkpoint](qualification/release-registry-2026-09-13/local.json) records 703 passing repository tests and the unresolved Docker Desktop registry fixture failure. This path has not completed a real Google Artifact Registry publication. Resume the existing registry test on Bazzite before qualifying publication.

The remaining qualification must publish the verified image once to staging and record the returned immutable registry digest. Staging evidence must bind that digest, migration checksums, configuration and secret versions, with the actual provider checks in the deployment ticket. The existing fixture tests cannot substitute for these observations.

Only terminal, passing staging evidence makes the same digest eligible for protected production approval. Promotion must preserve manifest bytes and verify the destination digest before updating a workload. It must run the candidate migration before serving revisions change, deploy tagged revisions with no traffic, qualify the real surface, and explicitly promote traffic. GitHub environment names and actual OIDC subjects must match the configured workload identity trust. Bootstrap/IAM activation remains outside the restricted release identity.

Rollback must select an earlier qualified stateless Cloud Run digest with compatible schema, secret versions and configuration. First-release failure keeps the route closed. Never rebuild an old commit as a substitute for the qualified bytes, reopen a sealed restore through migration grant repair, or revert to an unqualified legacy runtime. Artifact retention and registry pruning must preserve the eligible rollback images.

The full release remains incomplete until hosted CI, provider ownership and isolation, source permission/acquisition, staging evidence, restore/reopening, production approval and real traffic verification are established. No purchase, deployment, approval, upstream permission or external pilot use is established by this candidate tooling.
