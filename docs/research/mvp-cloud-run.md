# MVP Cloud Run architecture and operating envelope

Research date: 2026-09-12. Decision ticket: [Specify the accepted Cloud Run architecture and operating envelope](https://github.com/rubixhacker/LexCerta/issues/27). Repository evidence inspected at `7f5f3eaa6154a1834def2ebcd8af3c44d52bb38d`.

## Recommendation and boundary

Integration note: this independent research proposed five pilot organizations and retaining referenced source objects under the old policy. The parent MVP decisions select three organizations and a hard 30-day raw-source expiry with a bounded cache. Those later decisions govern implementation; the relevant research distinctions and migration risks remain below. See [Define the pilot customer, product promise, and MVP finish line](https://github.com/rubixhacker/LexCerta/issues/24) and [Establish CourtListener data, quota, and pilot-use constraints](https://github.com/rubixhacker/LexCerta/issues/26).

Implement the already accepted TypeScript Cloud Run architecture: Cloud SQL PostgreSQL holds authoritative records and serialized coordination; GCS holds immutable opinion objects; authenticated Cloud Run jobs perform maintenance; Artifact Registry digests identify promotable builds. Keep production and staging isolated. This does not revisit the rejected Worker runtime or introduce Valkey. The [accepted implementation reconciliation](https://github.com/rubixhacker/LexCerta/issues/11#issuecomment-5233345083) is the authority for these choices.

This document resolves the implementation design. It does not claim that Cloud Run has been implemented, provisioned, benchmarked, or verified live. Capacity figures and dollar thresholds below are recommendations, not purchase authorization. Production still needs the existing exact-artifact environment approval and staging evidence gate in [Deliver isolated staging and immutable promotion](https://github.com/rubixhacker/LexCerta/issues/11).

## Smallest useful deployment

Use Node 24 and the existing verification modules, with new Node HTTP, PostgreSQL, and GCS adapters. Preserve the stateless MCP public contract, three tools, bearer-key authentication, evidence outcomes, bounded source reads, and fail-closed behavior documented in [README](../../README.md). Leave protocol-version selection to the dedicated protocol decision; this platform design introduces no session storage.

| Component | Recommended configuration |
| --- | --- |
| Environment boundary | Separate staging and production GCP projects, SQL instances/databases, GCS buckets, runtime identities, secrets, CourtListener credentials, and LexCerta keys. One regional Artifact Registry build repository may supply the same immutable digest to both projects through explicit read grants. |
| Region | `us-central1` for services, SQL, GCS, jobs, and registry. This is a cost-conscious U.S. pilot default, not a measured latency or residency guarantee. |
| Public service | Node HTTP server, second-generation execution, 1 vCPU, 1 GiB, request-based billing, minimum 0, service and revision maximum 3, concurrency 8. No background maintenance loop. |
| Operator service | Separate deployment/entry point and identity; 1 vCPU, 512 MiB, minimum 0, maximum 1, concurrency 2. No admin routes or admin permissions in the public service. |
| SQL | Explicitly select **Enterprise**, PostgreSQL 18, general-purpose dedicated 1 vCPU / 3.75 GiB, zonal, initially 10 GiB SSD in each environment. Enable deletion protection, backups, and PITR. Use the same tier for staging qualification; a later measured cost reduction can change staging. |
| Opinion objects | Regional Standard GCS bucket, uniform bucket-level access, public access prevented, content-addressed immutable object names, SQL metadata pointing to exact GCS generation. |
| Maintenance | Same proven image with a dedicated job command; 1 vCPU / 512 MiB, one task, parallelism 1, bounded 10-minute execution. Separate identity. |
| Network | Cloud SQL Node connector over public IP with encrypted IAM-authorized connections and IAM database authentication; no authorized-network allowlist or public database password. This avoids a VPC connector/NAT service for the pilot. |

Google recommends starting single-threaded applications at 1 vCPU, and supports 1 GiB at that allocation. Concurrency 8 is deliberately below the platform default and must pass the workload gate. [CPU guidance](https://docs.cloud.google.com/run/docs/configuring/services/cpu), [concurrency guidance](https://docs.cloud.google.com/run/docs/about-concurrency)

PostgreSQL 18 is supported in Enterprise; newer PostgreSQL selections can default to Enterprise Plus, so the edition must be explicit. The 1 vCPU / 3.75 GiB combination fits Enterprise's published custom-machine limits. Zonal SQL means the pilot accepts a zone outage and maintenance interruptions; do not promise a highly available service. [Cloud SQL instance settings](https://docs.cloud.google.com/sql/docs/postgres/instance-settings)

The maintained Node connector supports `pg` and automatic IAM database authentication. Grant each database identity `cloudsql.client`, `cloudsql.instanceUser`, and narrowly scoped SQL grants; IAM connectivity does not replace SQL authorization. Pin connector/driver versions in the implementation lockfile. [Node connector source](https://github.com/GoogleCloudPlatform/cloud-sql-nodejs-connector), [IAM database login](https://docs.cloud.google.com/sql/docs/postgres/iam-logins)

## Admission, transactions, and source leases

The current algorithms should survive as pure state transitions; do not translate Durable Objects into one in-memory singleton. Current source evidence includes [coordinator](../../src/courtlistener/coordinator.ts), [budget lease recovery](../../src/courtlistener/budget-leases.ts), [key limiter](../../src/admission/api-key-limiter.ts), [opinion store](../../src/cache/d1-r2-opinion-source-store.ts), and [SQL schema](../../migrations/0005_opinion_source_cache.sql).

Recommended transaction design:

1. **Key authentication and admission:** address a key by public identifier, lock its canonical key row, validate environment/status/expiry/HMAC and current limits, count/append rolling-window admissions, and commit. Admin revoke, rotation, and limit changes lock the same row. An admission is linearized at this transaction; a request admitted before a later revocation may finish. Use DB-derived UTC time sampled after obtaining the lock. An unavailable database denies admission; there is no cached-positive authorization fallback.
2. **Service-wide CourtListener admission:** retain one locked state row per environment/CourtListener credential. In a short transaction, read and validate its state, apply the existing state-machine function, persist its reservation token and deadline, and commit. Missing/malformed state is failure, not permission to reset quota. PostgreSQL `SELECT ... FOR UPDATE` serializes competing updates until commit. [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html)
3. **HTTP boundary:** only after reservation commit may the process call CourtListener. Never hold a SQL transaction, row lock, or borrowed pool connection while awaiting CourtListener or GCS. Preserve the current 5-second upstream deadline, 10-second reservation lease, 100 pending-reservation bound, quota-sync accounting, and conservative expiry recovery. A lost response or crash does not refund an attempt that may have reached upstream. Reconciliation uses the recorded token; no blind HTTP replay after an ambiguous commit. [Budget constants](../../src/courtlistener/budget-state.ts), [bounded source API](../../src/courtlistener/case-law-api.ts)
4. **Outcome transaction:** lock the coordinator row again, recover expired reservations, record completion only for the matching live token, update circuits/quota, and commit. Duplicate, stale, and late completions must not debit twice, restore quota, or reopen a circuit incorrectly. Only retry short SQL-only transactions after proven rollback/deadlock; do not wrap external calls in transaction retries.
5. **Source leases:** claim a citation/opinion lease with a unique owner token, expiry, and monotonic fencing epoch. Fetch and normalize outside the transaction. Publishing locks the lease and corresponding source-state row, verifies token/epoch/expiry, applies existing freshness/reversal rules, and consumes the lease atomically. Lease release and negative-cache purge use the same ownership check and expected-state/version comparison. A late owner cannot publish over its successor.
6. **Object publication:** calculate the existing SHA-256/representation metadata; create the GCS object with `ifGenerationMatch=0`; on an existing object, verify bytes/hash, metadata, and generation rather than treating conflict as success. Only then publish its SQL pointer under the live source lease. A crash before SQL commit may leave an orphan; it must never leave a successful source state pointing at an absent/unverified object. GCS supports create-only generation preconditions and generation-specific deletion. [GCS preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)

Use PostgreSQL constraints and `timestamptz`, preserving the current bounded JSON schemas and uniqueness/foreign-key invariants. Keep migrations separate from server startup, applied once by the migration identity with an advisory lock and recorded checksum. Expand/contract schemas must support the previous qualified image while rollback remains possible. Port behavioral fixtures to real PostgreSQL; SQLite or SQL substring assertions do not prove row-lock correctness.

The public identity needs key-record reads and admission/coordinator/source-state writes, but no key issuance/revocation, DDL, or arbitrary object deletion. The operator identity can change keys plus append audit events; it cannot fetch CourtListener or read opinion objects. The job identity gets narrowly bounded retention/GC rights; the migration identity is separate. For GCS, object creation and reading can be granted separately from deletion; the public writer should not receive general storage administration. [GCS IAM roles](https://docs.cloud.google.com/storage/docs/access-control/iam-roles)

## Runtime deadlines and connection budget

Start with public pool maximum 5 per instance, admin 2, maintenance 2, migration 1; pools have minimum 0 and always release connections in `finally`. Nominal peak is 20 database connections (15 + 2 + 2 + 1). Reserve capacity for overlapping revisions: enforce SQL role connection ceilings of public 30, admin 4, maintenance 2, migration 1, leaving at least 20 connections for platform/operator recovery. Record the actual SQL `max_connections` before deployment and reject configuration whose sum leaves no headroom.

Use a 1-second pool acquisition timeout, 500 ms lock timeout, 2-second statement timeout, and 2-second idle-in-transaction timeout for online paths as initial tuning values. A bounded coordinator/database failure becomes the existing unavailable/indeterminate outcome, never a negative legal result. Cloud Run documents connection multiplication as instances scale, and its maximum-instance setting can briefly be exceeded; these are planning controls, not hard database safety guarantees. [SQL connection limits](https://docs.cloud.google.com/sql/docs/postgres/connect-run), [maximum-instance caveats](https://docs.cloud.google.com/run/docs/configuring/max-instances)

Set Cloud Run request timeout to 60 seconds with an application deadline of 55 seconds, propagated through source reads and body processing. Deadline exhaustion yields an explicit incomplete/indeterminate response when still possible. Keep the existing opinion-count and byte bounds; process opinion bodies incrementally rather than retaining 100 parsed trees. Trap `SIGTERM`, stop accepting work, abort external fetches, and drain/close pools within the shutdown window. Correctness must also survive `SIGKILL`; lease expiry is the recovery mechanism. Cloud Run provides a 10-second termination grace period and may terminate memory-exceeding instances. [Container contract](https://docs.cloud.google.com/run/docs/container-contract)

## Authentication and the operator control plane

The public service must accept requests through Cloud Run's public ingress configuration so ordinary MCP clients can present LexCerta bearer credentials. The application remains responsible for key authorization; only `GET /healthz` is unauthenticated at the application layer. Preserve strict route/header/body bounds and stateless protocol handling. [Public Cloud Run access](https://docs.cloud.google.com/run/docs/authenticating/public)

Keep the operator service's Cloud Run Invoker IAM check enabled with a specific operator principal allowlist. Provide a small CLI wrapper for issuing, rotating, revoking, and setting key limits; a dashboard is unnecessary for MVP. Each action must bind the application audit actor to a verified Google identity token with the correct audience and approved immutable subject, never an untrusted actor header/body. The wrapper can supply the complete token in an application-specific header for verification as well as platform authentication; verify actual header forwarding during staging tests. Secrets are shown once in the action response, never arguments, logs, or persisted plaintext. Existing rotation overlap, expiry, audit, and retention behavior is preserved. [Cloud Run IAM access](https://docs.cloud.google.com/run/docs/securing/managing-access), [identity tokens and audience](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)

Use distinct service accounts and Secret Manager secret versions for CourtListener credentials and the API-key HMAC pepper. CI uses workload identity federation scoped to repository/ref/environment, with no downloadable GCP service-account key. Public runtime cannot invoke the admin service. Staging credentials cannot authenticate in production even if a database row is copied accidentally.

## Telemetry and retention

Reuse the strict event schema and allowlist in [Operational telemetry](../../operations/observability.md). Emit sanitized structured completion/span events to a seven-day regional Cloud Logging bucket, with a generated correlation ID. Derive identifier-free operational metrics from those events. This is the recommended Cloud Run equivalent of the Worker log/trace path: retain span-shaped correlation records in Logging; do not enable automatic HTTP instrumentation or a separate Cloud Trace store for MVP. No per-request PostgreSQL ledger.

Cloud Run automatically generates request logs; sanitizing application logs alone is insufficient. Configure exclusions for raw request logs and any automatic trace export on **every** project/folder/organization sink that would persist them, then inspect the resulting live logging paths with hostile URL/query/header/error sentinels. Preserve safe system/OOM signals separately. Never emit raw request objects, SQL values, upstream errors, quotations, or credentials in caught or uncaught exceptions. Exclusions operate after log ingestion; make no promise that the hosting platform never processes request metadata. [Cloud Run logging](https://docs.cloud.google.com/run/docs/logging), [log routing](https://docs.cloud.google.com/logging/docs/routing/overview)

Seven days is configurable for application log buckets, but GCP's `_Required` infrastructure audit bucket retains events for 400 days and cannot use that custom period. Document this distinction in the privacy/operations copy; use resource names without customer content. [Bucket retention](https://docs.cloud.google.com/logging/docs/buckets), [required audit retention](https://docs.cloud.google.com/logging/docs/store-log-entries)

Schedule an authenticated hourly job for limiter cleanup and a daily 03:00 UTC lifecycle sweep. The hourly sweep removes admissions older than 47 hours, preserving the 24-hour rolling window while leaving a one-hour schedule margin before the 48-hour target. Logical expiry is checked on every relevant read; alert on missed maintenance rather than promising physical deletion during a platform outage. Lifecycle/audit records retain the existing one-calendar-year rules. Use SQL job ownership/fencing, bounded batches, and idempotent retries to handle duplicate/overlapping executions. Cloud Scheduler calls the Cloud Run Jobs API using an OAuth service-account token and job-specific invoker grant. [Scheduled jobs](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule)

Keep current positive-source freshness of 30 days, negative freshness of 24 hours, and reversal-confirmation interval of 24 hours. Freshness is not an object-deletion TTL. Referenced positive opinion objects remain available under the current source policy; no blanket GCS age deletion. Collect only unreferenced orphan objects after a 48-hour grace period, under source/GC fencing with a rechecked SQL reference and generation-match delete. Keep deletion marks that prevent a concurrent publisher reattaching an object being removed. [Opinion cache policy](../../src/verification/opinion-source-cache.ts), [citation cache policy](../../src/verification/citation-source-cache.ts)

Recommend seven daily SQL backups plus seven-day PITR, with a demonstrated isolated restore. Restored databases must run logical expiry/retention reconciliation before service reopening, and secrets/keys revoked after the restore point must stay revoked through an operator recovery inventory. Backup copies can outlive live-table expiry; document a maximum seven-day backup lag rather than claim immediate erasure from backups. A backup configuration is not restore proof. [Cloud SQL backup model](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/backups)

## Pilot economics and review thresholds

At published Iowa request-based rates, Cloud Run active resources cost $0.000024 per vCPU-second and $0.0000025 per GiB-second, plus $0.40 per million requests before free-tier allowances. An illustrative 100,000 requests causing 200,000 billed 1-vCPU/1-GiB instance-seconds costs about **$5.34 gross**, before free tier, jobs, startup, storage, network, registry, observability, and external API costs. This is an arithmetic example, not a measured per-request cost; concurrency changes billed instance time. [Cloud Run pricing](https://cloud.google.com/run/pricing)

The fixed SQL floor matters more: Iowa Enterprise general-purpose rates are $0.0413/vCPU-hour and $0.007/GiB-hour. One 1-vCPU/3.75-GiB instance at 730 hours is approximately $49.31 compute; 10 GiB SSD is another $1.70. Two isolated continuously running environments start near **$102/month before backups and other services**. Shared `db-g1-small` is cheaper but not covered by the SQL SLA and is not the recommended qualification baseline. Do not purchase committed-use discounts for an unproven pilot. Prices were read from Google's public pricing HTML because the browsing parser could not ingest its large page. [Cloud SQL pricing](https://cloud.google.com/sql/pricing)

Recommended initial pilot envelope: at most five invited organizations, operator-issued limits initially 10 MCP requests/minute and 100/day per key, and a separate aggregate CourtListener admission cap bounded by the actual approved upstream quota. Per-key MCP limits alone do not bound upstream fan-out. Start with a **$150/month combined GCP review budget**, alerts at 50/80/100% and forecast 100%; pause further invitations and investigate if forecast exceeds $150 or non-SQL spend exceeds $25/month. These are review thresholds, not an automatic outage trigger or spending authorization. Billing budgets do not cap spending. [Billing budgets](https://docs.cloud.google.com/billing/docs/how-to/budgets)

Review capacity when any of the following occurs: sustained RSS above 70% of the container limit; any OOM; p95 lock wait above 100 ms; pool utilization above 70% for 15 minutes; more than 1% infrastructure failures in a 15-minute window with at least 100 requests; forecast storage above 70% of the initial allocation; or upstream reservation/limit saturation. First inspect request shape, source-cache behavior, leaks, and SQL contention. Increase resources only from measured evidence. Before customer-facing latency promises, measure cold and warm p50/p95/p99 separately by tool and cache/outcome.

## Acceptance gates for implementation

| Gate | Required proof |
| --- | --- |
| Contract parity | Same official stateless MCP conformance, auth/error mapping, evidence outcomes, normalization, completeness, source freshness and refusal behavior through the emitted Node container. Legacy initialization/session fallback remains rejected. |
| Database concurrency | Real PostgreSQL, at least two service processes: simultaneous last-slot admissions, limit updates/revocation, quota reservations, half-open probes, duplicate completions, lease steal and stale publication. Exact quotas and one valid winner remain correct. |
| Crash integrity | Kill before/after reservation commit, before/after HTTP dispatch, after object upload, before/after source-state commit, and during retention. Restart shows conservative budget recovery, no false negatives, no stale-owner overwrite, and no dangling successful object pointer. |
| Cross-store integrity | Missing/corrupt/mismatched GCS object, conflicting immutable upload, GC/publish race, negative purge race, source contradiction, and restore with expired data all fail safely. Object hash and metadata are checked against the recorded version. |
| IAM and privacy | Public caller cannot administer; invalid/wrong-audience/wrong-subject operator tokens denied; runtime cannot read other-environment secrets/objects/SQL or invoke admin. Persisted logs/metrics/exports contain none of the injected legal-content/credential sentinels. |
| Workload qualification | Exact image at configured 1-vCPU/1-GiB/concurrency-8 envelope: bounded citation/quote maximums, 100-opinion cases, body-limit failures, slow/aborted upstream, cold startup, load/soak, and termination. No OOM; queue/connection/deadline behavior measured. Fixtures consume no CourtListener traffic. |
| Staging canary | After fixture qualification, one explicitly bounded live CourtListener canary through normal admission with staging credentials; record actual calls, responses, redacted evidence, and remaining quota. No uncontrolled live benchmark. |
| Delivery/rollback | Main-protected CI builds once; record commit, image digest, migration checksums, configuration, and terminal staging evidence. Deploy production at that digest with no traffic, smoke-test its tagged revision, then controlled traffic promotion after the existing approval gate. Roll back only to a qualified Cloud Run digest with compatible schema; on first launch, failure closes service rather than routing to legacy code. |
| Recovery/retention | Restore into isolation and rehearse revocation/retention replay; duplicate/missed scheduled jobs are detected; shutdown does not lose authoritative state; actual production retention/sink policies inspected. |

Cloud Run supports testing a tagged revision without routing normal traffic, followed by traffic migration and rollback. Those mechanisms do not themselves revert database migrations; compatibility and restore procedures remain application responsibilities. [Cloud Run rollout and rollback](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)

## Remaining live prerequisites

Implementation must establish actual GCP project/billing access, supported IAM organization policies, DNS/hostname ownership, isolated source credentials, upstream quota/commercial permission, SQL connection ceilings, logging-sink inheritance, secret delivery, exact-image CI, restore evidence, target-client compatibility, and a bounded canary result. None was provisioned or asserted present in this research. These are execution checks with chosen acceptance criteria, not reasons to reopen the accepted platform decision.
