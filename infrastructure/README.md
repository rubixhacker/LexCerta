# Cloud configuration

`environment/` defines the approved GCP portion of one LexCerta environment: Cloud Run services and jobs, attached identities, secret containers, separate GCS body and recovery buckets, Artifact Registry, GitHub workload identity, application-log routing and maintenance alerts. Apply it separately to existing, dedicated staging and production projects with distinct remote state. It does not create GCP projects, attach billing, purchase Neon, create database users, populate secrets or execute migrations.

This is implementation awaiting provider qualification. Local checks use Terraform's mock provider and Prometheus fixtures. No resources have been provisioned and no live IAM, log retention, alert delivery or production result is established. The [platform reconciliation](https://github.com/rubixhacker/LexCerta/issues/27#issuecomment-5649573236) and existing release approval govern deployment.

## Local checks

Use Terraform 1.16.2, the committed Google provider 8.2.0 lock file, Node 24.21.0 and Prometheus `promtool` 3.14.0. The repository workflow downloads the pinned tools, verifies the Prometheus archive checksum and runs these checks without Google credentials or a remote backend:

```sh
terraform fmt -check -recursive infrastructure
terraform -chdir=infrastructure/environment init -backend=false -input=false -lockfile=readonly
terraform -chdir=infrastructure/environment validate
terraform -chdir=infrastructure/environment test
node scripts/check-maintenance-alert.mjs
```

Set `LEXCERTA_PROMTOOL` to the local executable if it is not on `PATH`. The alert test evaluates the same PromQL template Terraform uses. It covers a never-created time series, healthy then missing work, wrong project/job labels, zero values and regular hourly progress. These checks cannot validate Google's metric ingestion delay or notification transport.

The [local qualification record](../operations/qualification/cloud-configuration-2026-09-12/local.json) identifies the configuration hashes, ten passing mocked Terraform scenarios and eight passing PromQL evaluations. It preserves the provider and parser failures corrected during validation and distinguishes local results from the unobserved hosted checks.

## Deployment inputs and order

Keep each environment's `*.tfvars` and backend configuration outside version control. Terraform state and saved plans are also ignored. Supply real, verified values; the test fixtures' project and customer names are synthetic.

1. Establish owned GCP projects, billing authorization, independent Neon projects, remote-state storage and the required owner access. Inventory existing project and inherited IAM, logging sinks, trace export and organizational constraints. Do not apply this configuration to a shared or unidentified project.
2. Initialize the GCS backend separately for each environment, using an access-controlled state bucket and different prefixes. Do not use `-backend=false` for deployment and do not reuse staging state for production. Supply `project_id`, `environment` and verified `operator_members` (`user:email` IAM members). Leave `release = null` for foundation creation.
3. Prepare the restricted Neon roles and database ownership described in [database migrations](../operations/database-migrations.md). Set the agreed direct Ohio endpoint, five-minute suspension, initial 0.25–1 CU autoscaling and recovery retention. Store distinct database passwords, an environment pepper and the permitted upstream token as Secret Manager versions outside Terraform. The configuration creates only secret containers and access grants; no secret data resource exists.
4. Publish the tested image into the environment's `lexcerta/runtime` repository. Production receives the same digest bytes by promotion/copy, without rebuilding. Populate `release` with `image_digest`, `build_id`, `neon_host`, `courtlistener_credential_id`, one to three `pilot_customers`, and numeric versions for all six secrets. Tags, `latest`, pooler hosts and all-zero build IDs are rejected. Keep `activate = false` while preparing the services and jobs.
5. Run the packaged migration job and require success before any application traffic. Check restricted roles, key issuance and environment isolation, real GCS behavior, log privacy and recovery. Run maintenance manually, verify both durable phases, then exercise actual missing/failed-job alert delivery. `notification_channels` references already verified channels in this environment's project; no recipient is invented or subscribed by this module.
6. Follow the staging qualification and existing protected production approval before setting `activate = true`. This enables public IAM invocation and unpauses the hourly schedule. LexCerta bearer-key authentication remains in the public application. The operator is always IAM-protected. The initial missing-job alert is expected until healthy maintenance has run; a private release can exercise monitoring before activation.

For later releases, migrate using the candidate image before updating serving revisions, following expand/contract compatibility. Terraform does not execute SQL or order a cloud job's completion for you. Do not set `release = null` to roll back: it asks Terraform to destroy the workload resources. Roll back to an eligible prior image digest with the compatible secret versions, preserving current durable state and release approval.

`release.secret_versions` uses these keys: `database_public`, `database_operator`, `database_job`, `database_migrator`, `api_key_pepper`, `courtlistener`. Password rotation creates a new secret version outside Terraform, changes only the affected reference and requires successful identity/connection qualification before disabling the old version. Pepper rotation is a credential migration, not ordinary password maintenance.

## Runtime and identity boundaries

Both services use request-based billing with zero minimum instances, one CPU, no session affinity and no startup CPU boost. The public service has 1 GiB, concurrency eight, maximum three instances and a 60-second platform timeout around its 55-second application deadline. The operator has 512 MiB, concurrency two and maximum one instance. Each service and revision has an explicit maximum. Cloud Run maxima are operational controls, not a guaranteed billing cap.

Maintenance uses one task at one CPU/512 MiB, a 600-second task timeout and one task retry. Scheduler submits once per UTC hour, with one bounded submission retry. The job decides daily 03:00 UTC lifecycle eligibility from database time. An uncertain submission can produce duplicate executions; the tested database fence serializes their work. Migration uses a separate identity, one task and no automatic task retry. Scheduler has only job invocation permission and cannot invoke migrations or the operator. The Google Jobs API requires an OAuth access token from Scheduler. [Scheduled jobs](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule).

Public, operator, job and migration identities each receive only the corresponding database-password secret. Public/operator share the environment pepper; only public receives the upstream token. Public storage access is get/create/delete on `opinions/`, including bounded capacity eviction. Maintenance can get/delete those bodies and list the dedicated bucket, but cannot publish. Operator and migration identities have no source-object access. IAM object-name conditions cannot restrict listing; that permission is therefore limited to the dedicated bucket. [Storage IAM conditions](https://docs.cloud.google.com/storage/docs/access-control/iam-conditions).

The operator additionally receives create/get permission on its environment's `restrictions/v1/` prefix in a separate `${project_id}-lexcerta-recovery` bucket. It persists revocations and rotation expiry ceilings before SQL mutations. No runtime identity receives delete, overwrite, metadata-update or bucket-list permission there. This bucket has no automatic deletion; [record retention and complete restore/replay qualification](../operations/recovery-journal.md) remain open. There is no new always-running service for this journal.

The operator invoker is separate from every runtime identity. Verified humans may impersonate it; its immutable Google subject is the application allowlist entry. It may also invoke the private public-service canary before activation, using a Google ID token for the public URL in `X-Serverless-Authorization` and a LexCerta key in `Authorization`. The configured operator audience uses Cloud Run's documented deterministic URL, also registered as a custom audience. Real ingress and ID-token forwarding still require the canary. [Cloud Run URLs](https://docs.cloud.google.com/run/docs/triggering/https-request), [custom audiences](https://docs.cloud.google.com/run/docs/configuring/custom-audiences).

GitHub trust requires the verified numeric repository and owner IDs, `main`, this environment's OIDC subject and `.github/workflows/release.yml`. The [release candidate workflow](../operations/release.md) now builds and retains fixture-qualified image bytes; cloud authentication, staging and promotion remain unimplemented. Main and the production environment protections were configured and independently verified on September 13. The read-only preflight passes; no production approval was granted. The future production job must reference that protected environment. The release identity may update the existing workloads, execute their jobs, observe status, attach the four runtime identities and publish repository artifacts. It cannot change IAM, read Secret Manager directly, impersonate the operator invoker or mint downloadable cloud keys through this configuration. Updating an image still gives trusted release code access to that workload's credentials, so branch/workflow/environment protection is essential. [GitHub workload identity](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines).

## Logging, alerts and remaining qualification

The project `_Default` sink excludes LexCerta service/job logs. A separate sink keeps only the known structured application events from stdout/stderr in a seven-day regional bucket. Raw request entries, SDK text warnings and unrecognized events do not pass that sink. These filters route whole log entries; they are not a field-redaction engine. The runtime must continue emitting only its bounded, tested event schemas.

Other project sinks and inherited folder/organization sinks evaluate independently. They must receive equivalent workload exclusions and be inspected before activation; the module's output exposes the filter for that work. Cloud Trace export and actual persisted hostile-sentinel absence remain live checks. The `_Required` audit bucket keeps Google's mandatory retention; the application bucket does not shorten it. [Log routing](https://docs.cloud.google.com/logging/docs/routing/overview), [sink authorization](https://docs.cloud.google.com/logging/docs/export/configure_export_v2).

The healthy-maintenance metric contains no customer or source labels. A finished invocation qualifies only when the database reports both cleanup and lifecycle progress current. Busy/idle invocations cannot change that durable progress. One alert detects no healthy events over two hours, including a time series that never existed; another detects partial/failed runs and overdue database slots. A missing job need not emit a failure log to be detected. The database checks the 26-hour lifecycle threshold, avoiding Google's 25-hour lookback limit for user-defined log metrics. Ingestion and hourly scheduling can add delay; measure this and exercise alert delivery in staging. [PromQL monitoring](https://docs.cloud.google.com/monitoring/promql), [alert query limits](https://docs.cloud.google.com/monitoring/alerts/using-promql).

Automatic object lifecycle deletion at age 30 days is a backstop. Read expiry and fenced maintenance enforce application policy; real physical-deletion lag remains unmeasured. Versioning and soft deletion are disabled for bodies. Source bucket and secret destruction are protected, and the image registry retains rollback candidates until delivery can safely prune reviewed digests.

Still open: Neon/bootstrap automation and actual provider grants, inherited sinks/trace privacy, GCP and Neon cost notifications and combined $25 forecast review, bounded image/backup retention, complete provider restore/reopening, hosted CI, immutable promotion/rollback, written CourtListener permission and external pilot use. The thirty-minute local fixture soak and local sealed SQL replay now have separate qualification records; these definitions do not replace the remaining provider gates.
